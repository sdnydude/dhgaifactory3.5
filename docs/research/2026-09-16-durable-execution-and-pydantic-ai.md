# Durable execution engine and Pydantic AI 2.x building blocks for the CME rebuild

Date: 2026-09-16. Documentation research against primary vendor sources; URLs inline. Three claims were re-verified in the main session: DBOS's tracing docs name Langfuse as a supported provider with the `enable_otlp` / `otlp_traces_endpoints` keys; DBOS documents durable timeouts persisting across restarts with no maximum; Temporal's history cap is 51,200 events or 50 MB (the 2 MB payload limit is on a separate Temporal page and stands as the researcher's claim). Registry insights c3318c6f and ecba9058 carry the two non-obvious findings.

## Decisive conclusions

- **Engine: DBOS.** A library against the Postgres 15 already running, zero added containers, and its own observability docs name Langfuse directly. Temporal is MIT throughout but costs four services plus Postgres plus Elasticsearch and imposes a 2 MB payload and 51,200-event history ceiling that a long-lived grant-package agent will hit. Prefect is five containers with no OpenTelemetry story. Restate has the best human-in-the-loop story and a first-party Langfuse plus Pydantic AI page but is BSL 1.1 with a Python SDK at 1.0 since June 2026 and a streaming method that raises.
- **Keep the multi-day approval gate out of the engine.** Pydantic AI's deferred tools end the run; persist message history to Postgres by conversation id; resume with the approval results. The wait is a database row, not a parked workflow holding a worker.
- **Two things to settle before any build:** AG-UI over a durable run with tool approval does not work end to end today (pydantic-ai issue 6580, open), and every engine buffers streaming across the durable boundary, so decide whether the UI needs token-level streaming or step-level progress bridged over our own queue or websocket. And Langfuse v4 self-hosted pulls in ClickHouse, Redis and MinIO alongside Postgres, the heaviest dependency in the stack.
- **Evals correction:** the `Python` evaluator no longer exists in pydantic-evals (removed for security, PR 2808); `LLMJudge` defaults to an OpenAI judge and must be overridden; pydantic-evals ships no CI recipe, Langfuse does (`langfuse/experiment-action` with a regression gate).
- **Document rendering: Pandoc** from agent-emitted Markdown plus CSL-JSON, DOCX via a reference template and PDF via WeasyPrint. Native citation handling, fully offline.

## 1. Durable execution engine choice for Pydantic AI 2.x

Pydantic AI 2.43.0 lists five co-maintained engines (Temporal, DBOS, Prefect, Restate, AWS Lambda durable functions) plus external integrations for Kitaru and Airflow (https://pydantic.dev/docs/ai/capabilities/durable_execution/overview/); PyPI extras exist for `dbos`, `prefect` and `temporal`; Restate ships inside its own MIT SDK. In 2.x durability is a capability (`DBOSDurability`, `PrefectDurability`, `TemporalDurability`) attached via `capabilities=[...]`, transparent outside a workflow; the older wrapper classes are deprecated for removal in v3. The agent run loop is the workflow and model requests, tool calls, MCP communication and event-stream handlers become steps. Migration trap: the capability no longer wraps `run()`, so porting constructor arguments and calling `agent.run()` directly produces a run that works but is not durable. DBOS's own integration page still documents the deprecated wrapper (https://docs.dbos.dev/integrations/pydantic-ai).

**DBOS** runs fully in-process as a library against Postgres or SQLite, no orchestration server (https://docs.dbos.dev/architecture); `dbos` 2.31.1 (2026-09-08, MIT, Python 3.10 to 3.14). Human-in-the-loop primitives: `DBOS.recv(topic, timeout_seconds)` inside the workflow, woken by `DBOS.send(...)` from an HTTP endpoint, status via `DBOS.set_event`/`get_event` (https://docs.dbos.dev/python/tutorials/workflow-communication); a dedicated AI guide shows exactly that shape (https://docs.dbos.dev/ai/hitl, https://docs.dbos.dev/python/examples/agent-inbox). Timeouts are durable and stored in the database; durable sleep is documented for days, weeks or months; no hard maximum (https://docs.dbos.dev/python/tutorials/workflow-tutorial). `recv` holds a worker slot while waiting. Free CLI introspection (`dbos workflow list|get|steps|cancel|resume|fork`, https://docs.dbos.dev/python/reference/cli); the dashboard, Conductor, is paid ($99 or $499 per month; self-hosting needs a production licence, https://www.dbos.dev/pricing, https://docs.dbos.dev/production/hosting-conductor). OTel: `enable_otlp` plus `otlp_traces_endpoints`, step spans parented under workflow spans, `PropagateOtelContext`, and Langfuse named as a provider (https://docs.dbos.dev/python/tutorials/logging-and-tracing). Two negatives: no selective non-retryable exceptions, so with step retries on, a misconfigured agent burns its full retry budget before failing; and no per-tool step configuration.

**Temporal** needs four server roles plus a UI server, persistence on Cassandra, MySQL or PostgreSQL, and Elasticsearch for advanced visibility (https://docs.temporal.io/self-hosted-guide/deployment); the official docker-compose repo is archived, use https://github.com/temporalio/samples-server/tree/main/compose. MIT throughout including the UI; `temporalio` 1.33.0. Waits via signals, updates and `wait_condition()` with no documented limit and an infinite default execution timeout. The binding constraint is history: 51,200 events or 50 MB per execution, warning at 10,240 events or 10 MB, and a 2 MB payload limit on every activity argument and return (https://docs.temporal.io/workflow-execution/limits); a large deps object is copied into history on every activity, so a long-lived grant agent hits the cap. Oversized values into an activity fail as a workflow-task failure that retries indefinitely. `RunContext` inside activities is a limited copy; sub-agent delegation usage never accrues to the parent run under Temporal (https://github.com/pydantic/pydantic-ai/issues/6886). Model activities default to unbounded retries unless configured. Observability plugins (Logfire, Temporal's OpenTelemetry plugin, Langfuse endpoint) are not documented as composing.

**Restate** is one binary and one volume with a bundled admin UI, the only Pydantic-AI-specific human-in-the-loop page (awakeables resolved by HTTP, the agent suspends rather than idles, https://docs.restate.dev/ai/patterns/human-in-the-loop.md) and the only first-party Langfuse plus Pydantic AI page (https://docs.restate.dev/ai/ecosystem-integrations/langfuse.md). Against it: BSL 1.1 converting to Apache 2.0 after four years (internal use is within the grant, but not OSI open source); Python SDK 1.0.0 on 2026-06-23; `RestateAgent.run_stream` raises.

**Prefect** is Apache 2.0 and widely adopted but costs five containers (https://docs.prefect.io/v3/how-to-guides/self-hosted/docker-compose.md); an arbitrary-duration wait needs `suspend_flow_run` plus a deployment plus persisted results, because `pause_flow_run` blocks in memory and fails at its 3600-second default; no OpenTelemetry story in its docs.

All four buffer streaming across the durable boundary, and AG-UI over a durable run is not wired: calling a streaming method from a UI adapter in a web endpoint is a plain non-durable run; to serve a durable agent behind an API, the endpoint starts or signals a workflow and bridges events back (https://github.com/pydantic/pydantic-ai/issues/6580, open as of 2026-09-11). Neither durable-execution page documents a human-in-the-loop API and the deferred-tools page never mentions an engine.

## 2. Pydantic AI 2.x building blocks

**Capabilities** bundle tools, hooks, instructions, model settings and model selection behind `capabilities=[...]` (https://pydantic.dev/docs/ai/core-concepts/capabilities/); built-ins include Thinking, WebSearch, WebFetch, MCP, Instrumentation, Hooks, Toolset, ReinjectSystemPrompt, ProcessHistory, ProcessEventStream (https://pydantic.dev/docs/ai/capabilities/overview/). `capabilities` is also a per-run parameter, merged with the agent's, alongside `output_type`, `message_history`, `deferred_tool_results`, `conversation_id`, `run_id`, `model`, `instructions`, `deps`, `model_settings`, `usage_limits`, `toolsets`, `spec` and others (https://pydantic.dev/docs/ai/api/pydantic-ai/agent/); per-run capabilities raise inside a DBOS or Temporal workflow except Instrumentation. **AgentSpec** defines agents declaratively in YAML or JSON (model, instructions, capabilities, model settings, output schema, deps schema, retries, end strategy, tool timeout, metadata, templated strings resolved against deps), loaded by `Agent.from_file()` (https://pydantic.dev/docs/ai/core-concepts/agent-spec/). That is the natural shape for per-client and per-supporter variation without forking Python.

**Deps and RunContext** carry tenant context: type at construction, instance per run, reachable in tools, instructions and validators; `agent.override(deps=...)` for tests (https://pydantic.dev/docs/ai/core-concepts/dependencies/).

**Toolsets**: FunctionToolset, CombinedToolset, FilteredToolset, PrefixedToolset, ApprovalRequiredToolset, DeferredLoadingToolset, ExternalToolset and others (https://pydantic.dev/docs/ai/tools-toolsets/toolsets/); under a durable capability register everything at construction with stable ids. MCP servers via `MCPToolset` or the `MCP` capability (https://pydantic.dev/docs/ai/capabilities/mcp/). **Hooks** cover run, node, model-request, tool-validate, tool-execute and output-processing points and can raise `ModelRetry`, `ToolFailed` or `SkipModelRequest` (https://pydantic.dev/docs/ai/core-concepts/hooks/).

**Human approval, engine-independent**: `@agent.tool(requires_approval=True)` or raising `ApprovalRequired` ends the run with `DeferredToolRequests`; resume with `message_history` plus `deferred_tool_results=DeferredToolResults(approvals={call_id: ToolApproved(...) | ToolDenied(...)})`, new run id, same conversation id (https://pydantic.dev/docs/ai/tools-toolsets/deferred-tools/). Message history round-trips through `all_messages_json()` and `ModelMessagesTypeAdapter`, keyed by conversation id (https://pydantic.dev/docs/ai/core-concepts/message-history/). A days-long approval is a Postgres row. The docs state approval is not an authorization boundary; sensitive actions need server-side validation.

**Output**: `ToolOutput` (default, works across models), `NativeOutput` (provider structured outputs), `PromptedOutput` (least reliable); `@agent.output_validator` raising `ModelRetry` against a retry budget (https://pydantic.dev/docs/ai/core-concepts/output/). **Usage limits**: request, input, output and total tokens, tool calls, per-request input tokens, and a USD `cost_limit`; `RunUsage.cost` is best-effort and `None` for unpriced models such as Ollama (https://pydantic.dev/docs/ai/core-concepts/agent/).

**Models**: `provider:model` strings for Anthropic; `OpenAIChatModel(..., base_url='http://localhost:11434/v1')` for Ollama and OpenAI-compatible endpoints; `FallbackModel` for failover (https://pydantic.dev/docs/ai/models/overview/). **Instrumentation**: `Instrumentation(InstrumentationSettings(...))`, `Agent.instrument_all()`, OpenTelemetry GenAI semantic conventions; Logfire optional; Langfuse named as a backend (https://pydantic.dev/docs/ai/integrations/logfire/). Self-hosted Langfuse contract: `OTEL_EXPORTER_OTLP_ENDPOINT=http://<host>:3000/api/public/otel`, `OTEL_EXPORTER_OTLP_HEADERS=Authorization=Basic <base64(pk:sk)>,x-langfuse-ingestion-version=4`, HTTP only, gRPC unsupported, and the ingestion-version header avoids up to ten minutes of delay (https://langfuse.com/integrations/native/opentelemetry). `include_content=False` excludes prompts, completions and tool arguments from telemetry, the switch for any CME-mode run.

**Multi-agent**: single agent, then delegation (sub-agent awaited inside a tool, passing `ctx.usage`), then programmatic hand-off, then graphs, then deep agents (https://pydantic.dev/docs/ai/guides/multi-agent-applications/). The graph docs warn to consider other approaches first (https://pydantic.dev/docs/ai/graph/graph/); use `pydantic-graph` only where the pipeline genuinely needs a state machine with conditional routing. Do not build on graph state persistence; durable capabilities supersede it.

## 3. Evals

`pydantic-evals` 2.43.0 (https://pypi.org/project/pydantic-evals/): `Dataset` of `Case(name, inputs, metadata, expected_output, evaluators)`, YAML or JSON serialization with an auto-generated schema (https://pydantic.dev/docs/ai/evals/how-to/dataset-serialization/). Built-in evaluators: EqualsExpected, Equals, Contains, IsInstance, MaxDuration, HasMatchingSpan, LLMJudge, GEval, and agent-shaped ToolCorrectness, TrajectoryMatch, ArgumentCorrectness, MaxToolCalls, MaxModelRequests, plus report-level statistics (https://pydantic.dev/docs/ai/evals/evaluators/built-in/). The `Python` evaluator was removed for security (PR 2808). Custom evaluators subclass `Evaluator` with sync or async `evaluate(ctx)`; a version method stamps results. `LLMJudge` defaults to an OpenAI judge model; override with `set_default_judge_model('anthropic:...')` or per evaluator (https://pydantic.dev/docs/ai/evals/evaluators/llm-judge/). Reports carry scores, labels, assertions, metrics, durations, trace and span ids per case; token usage is not a first-class field. No CI recipe is documented. Span capture is gated on the logfire extra configured with `send_to_logfire=False` (https://pydantic.dev/docs/ai/evals/how-to/logfire-integration/). Online evaluation emits one OTel log event per result with pluggable sinks (https://pydantic.dev/docs/ai/evals/online-evaluation/).

Langfuse v4 (4.37.0 on 2026-09-16): datasets, dataset runs, experiments, LLM-as-a-judge, annotation queues, scores and prompt management are free OSS; enterprise adds project-level RBAC, protected prompt labels, retention policies, audit logs, masking, SCIM (https://langfuse.com/pricing-self-host). Self-hosting is six components (web, worker, Postgres, ClickHouse, Redis or Valkey, S3 or MinIO); the compose path is for trials, Kubernetes for production (https://langfuse.com/self-hosting). Experiments via `dataset.run_experiment(...)` (https://langfuse.com/docs/evaluation/experiments/experiments-via-sdk); scores via `create_score` or the public API (https://langfuse.com/docs/evaluation/evaluation-methods/scores-via-sdk). The Pydantic AI integration page covers tracing only (https://langfuse.com/integrations/frameworks/pydantic-ai).

The two are parallel systems with no documented bridge. What exists is a generic attribute contract for experiments over OTel (https://langfuse.com/integrations/native/opentelemetry/experiments); a post-run loop calling `create_score` per case using the report's trace and span ids is roughly thirty lines that we write. Langfuse ships the CI story: `langfuse/experiment-action` with a regression gate that blocks a PR when any previously passing case regresses (https://langfuse.com/docs/evaluation/experiments/experiments-ci-cd).

## 4. AG-UI from Pydantic AI in detail

`AGUIAdapter` parses `RunAgentInput` (message history, shared state validated against Pydantic models, frontend tools, client context) and returns an SSE stream of AG-UI events (https://pydantic.dev/docs/ai/integrations/ui/ag-ui/). Entry points: `dispatch_request()` for Starlette and FastAPI (recommended), `run_stream()` for custom frameworks, or a standalone app. Shared state via `StateDeps[YourState]` or the `StateHandler` protocol; the adapter mutates state, so copy per request; `StateSnapshotEvent` persists updates through history. Approval: with `output_type=[str, DeferredToolRequests]` and an approval-required tool, the adapter ends the stream with `RUN_FINISHED` whose outcome type is `interrupt`; the client resumes by POSTing a new input carrying `resume[]` entries of approved and edited arguments. `CustomEvent` pushes real-time updates from tools. Client context entries describe a request and never establish who is making it: authenticate server-side, pass client entries to the model as tool output, never as instructions; frontend system prompts are stripped by default.

Reconnection: no resumable stream and no polling API. For long or durable runs the agent does not run inside the request; events reach the API edge over a transport of their own (a durable workflow, a queue, a websocket fan-out) and the `UIEventStream` subclass is used as a standalone encoder (https://pydantic.dev/docs/ai/integrations/ui/overview/). Pass explicit `thread_id` and `run_id` (defaults are re-minted on replay); the thread id maps to the agent's conversation id. Client disconnects surface as `asyncio.CancelledError`; interrupts need `ag-ui-protocol` 0.1.19 or later. AG-UI plus a durable agent plus approval does not work end to end today (issue 6580).

## 5. Document output

Pandoc as the renderer: agents emit per-section Markdown plus a CSL-JSON bibliography with citations as `[@pmid12345]`; `--citeproc`, `--csl` (AMA or Vancouver), `--bibliography`, `--reference-doc=dhg-grant-template.docx` for a funder-branded Word file, and PDF via `--pdf-engine=weasyprint` from the same source (https://pandoc.org/MANUAL.html). python-docx 1.2.0 cannot add headers, footnotes or a real table of contents (https://python-docx.readthedocs.io/en/latest/user/documents.html); docxtpl 0.20.2 stays in reserve for field-by-field funder forms. WeasyPrint 70.0 is the PDF engine (CSS Paged Media, footnotes, cross-references) but has no bibliography engine. Anthropic's server-side code execution and document skills are API-available but the container has no outbound network, no package installs, and is not zero-data-retention eligible, which disqualifies it for pharma-grade grant content on a self-hosted stack.

## Recommended stack for the rebuild

1. DBOS (`pydantic-ai-slim[dbos]`, `DBOSDurability`) as the durable engine.
2. Do not park a workflow for human approval; end the run on `DeferredToolRequests`, persist message history by conversation id, resume with the results.
3. Scope DBOS durability to the generation phase (minutes to hours), so a worker never holds a slot overnight.
4. Cap or disable DBOS step retries.
5. Visibility on the free DBOS CLI plus Grafana, not Conductor.
6. Reject Temporal for this deployment (infrastructure and history ceiling).
7. Reject Prefect (containers, no OpenTelemetry, pause semantics).
8. Keep Restate as the documented fallback, not now (BSL, SDK age, streaming raises).
9. Agent configuration as AgentSpec YAML loaded by `Agent.from_file()`, with per-run overrides, for per-client and per-supporter variation.
10. Tenant and CME-mode context in deps and RunContext, never module state.
11. Register every toolset at construction with stable ids and a stable agent name.
12. Default to `ToolOutput` with output validators raising `ModelRetry`.
13. `UsageLimits` with cost, request and tool-call limits on every pipeline run.
14. Instrument with `Agent.instrument_all()` to self-hosted Langfuse over HTTP with the ingestion-version header; `include_content=False` on CME-mode runs.
15. Author evals in pydantic-evals, override the judge to Anthropic, use trajectory evaluators for pipeline shape, bridge to Langfuse scores with a small adapter, and gate CI on Langfuse experiments.

Settle before building: token-level streaming versus step-level progress during durable generation; and the operational weight of Langfuse v4 self-hosted.
