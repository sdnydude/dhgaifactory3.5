# CME rebuild: the copilot route versus the original pipeline route

Date: 2026-09-16. Author: Claude (Fable 5.1), for Stephen Webber.
Inputs: a code inventory of the existing LangGraph CME pipeline (five headline findings re-verified line by line), a documentation survey of CopilotKit, AG-UI, assistant-ui, Pydantic AI and the Vercel AI SDK with a source beside every claim (appendix), and package versions confirmed against npm and PyPI on 2026-09-16.

This answers the questions asked on 2026-09-16: what is new and better in the copilot approach since it was first chosen, what packages have grown up around it, how it compares to the original CME pipeline on power and ease of build, features and benefits, capability gaps, ongoing development need, per-client modularity toward a SaaS settings model, scalability and load, user journey, and maintainability by Claude.

## 1. What the two routes actually are

**The original route** is the LangGraph pipeline as built: fourteen agents, each a fixed chain of prompt calls producing free text, three orchestrators that run them in sequence, a human-review pause that is switched off by default, output as markdown pushed to the registry and Google Drive, and a separate inbox page in the Next.js app that polls LangGraph Cloud for pending reviews. The user submits an intake form, waits, and reviews a finished document.

**The copilot route** is agents built on Pydantic AI, exposed to the browser over the AG-UI protocol, and driven from a chat-and-document surface inside the Next.js module of the Open WebUI portal. The user works with the agents while the document is being built: sees progress and reasoning, is asked to approve specific steps, edits shared state the agents also read, and gets interface elements (tables, checklists, citation panels) generated by the agents rather than plain text.

These are not opposites. A grant package still takes hours of agent work and must survive restarts; the copilot route needs a durable pipeline underneath it. The real comparison is between "batch pipeline with an inbox at the end" and "durable pipeline with a live collaborative surface on top." The second contains the first.

## 2. What is new since mid-2026

The stack chosen in mid-2026 has changed underneath in five ways that matter.

- **Pydantic AI reached 2.0 on 2026-06-23** and is now at 2.43. Version 2 introduced "capabilities," a composable unit that bundles an agent's tools, hooks, instructions and model settings. That is the primitive a per-client configurable product needs: a client's rules become a capability, not a code fork.
- **Durable execution is first-party.** Pydantic AI co-maintains integrations with Temporal, DBOS, Prefect, Restate and AWS Lambda durable functions. An agent run can pause for days waiting on a human and resume after a server restart. The original pipeline's review pause depends on LangGraph Cloud's checkpointing, which the inventory could not confirm is even active for these graphs.
- **AG-UI became the common wire.** Pydantic AI, Google ADK, AWS Strands, Bedrock AgentCore, Microsoft Agent Framework, Mastra, Agno and LlamaIndex all speak it first-party. It gained event types for activity, reasoning and sub-agents. Pydantic AI's adapter turns a tool marked "requires approval" into a protocol-level interrupt, which is the human-in-the-loop mechanism the CME product needs, built in rather than bolted on.
- **assistant-ui shipped its own AG-UI adapter** (September 2026). CopilotKit is no longer the only client that can drive an AG-UI agent. The two libraries are now alternatives over the same backend, which is the escape hatch from lock-in.
- **CopilotKit split into a free runtime and a paid layer.** The runtime (agents, shared state, generative UI, human-in-the-loop, Pydantic AI integration) is open source. Durable cross-device threads, the admin inspector, multi-tenancy and analytics are the paid "Intelligence" tier, self-hostable from the Team plan upward on Kubernetes with Postgres and Redis. Persistence is the line to plan around.

Two more facts to carry: the Vercel AI SDK went to version 7 and ESM-only, a migration the AG-UI-native path avoids entirely; and Langfuse was acquired by ClickHouse in January 2026 with open-source and self-hosting commitments, so the self-hosted version should be pinned and its trace ingestion validated before it becomes the CME audit trail.

## 3. Features and benefits, side by side

| Capability | Original pipeline (as built) | Copilot route (Pydantic AI + AG-UI) |
|---|---|---|
| Output correctness | Free text parsed by hand; a failed parse silently empties a section | Typed, validated outputs on every handoff; a bad output is an error, not a blank |
| Grounding of medical claims | Three of fourteen agents call PubMed or Perplexity; narrative agents write from model memory; citation checker never wired in | Tools are first-class: PubMed, the medkb retrieval service, the registry; the model must call them and the trace shows it did |
| Human review | Pause exists but defaults to off; review identity is an unauthenticated email parameter | Approval is a protocol event tied to a specific tool call; identity comes from the portal session |
| Visibility while running | None until the inbox item appears | Live progress, reasoning summaries, sub-agent events streamed to the surface |
| Editing during a run | Not possible; re-run the pipeline | Shared state: user edits the objectives list, agents continue from the edit |
| Surviving restarts and long waits | Depends on LangGraph Cloud checkpointing (unverified for these graphs) | Durable engine (Temporal or DBOS) pauses and resumes runs across restarts and days |
| Per-client configuration | None; one global prompt set and API key | Capabilities plus per-run dependencies carry the client's rules, style, compliance profile |
| Evals | Regex style checks only; nothing measures truth or compliance | pydantic-evals datasets plus Langfuse scores on every version of every agent |
| Cost tracking | Computed per call, never stored | Usage on every run, exported by OpenTelemetry into Langfuse and Prometheus |
| Model choice | Claude only, hardcoded | Any provider per agent, including Ollama for drafts and Claude for final passes |
| Other channels | None | Same agent reachable from Slack or Teams through CopilotKit's channels SDK, if wanted |

The benefit that matters most for a medical-education business is the second row combined with the eighth: the copilot route makes it structurally hard to ship an ungrounded claim, and measurable when it happens.

## 4. Capability gaps

**Gaps in the original route** are the audit's gap list: review off by default, no structured outputs, ungrounded narratives, two dead agents, silent data loss between the parallel design agents, an unbounded compliance loop, no tenancy, spoofable review identity, no PHI posture, no evals, no persisted cost. None of these are patchable in place without rewriting the agents, which is why the rebuild decision stands.

**Gaps in the copilot route today**, stated honestly:

- Thread persistence across devices is either the paid CopilotKit tier or our own thread store in the registry database. Building our own is a bounded job (threads, messages, run state, per-user) and keeps us on the free runtime.
- The AG-UI SDKs are pre-1.0 (0.0.59 for the JavaScript client) and the protocol is versioned by date, not by compatibility promise. Pin exact versions and expect an upgrade window each quarter.
- CopilotKit's documentation calls the open-source core Apache 2.0 while its repository says MIT. Different patent terms. Get that clarified in writing before it carries CME revenue.
- Nothing in this stack provides a per-tenant settings panel. That is our build, against the registry, in every scenario.
- The long-document workflow (a full grant package) is a multi-hour run. The copilot surface shows it and steers it, but the durable engine does the work; choosing and operating that engine is new infrastructure. DBOS runs on the Postgres we already have; Temporal is more battle-tested and brings its own cluster.

## 5. Ongoing development need

The original route needs a rewrite to reach production, then continued maintenance of hand-parsed text and hand-wired HTTP calls in fourteen files. The copilot route needs an initial build of the shared pieces (AG-UI endpoint, thread store, tenant context, durable engine) and then per-agent work that is mostly typed schemas, tools and evals. Release cadence is the real ongoing cost: Pydantic AI ships minor versions every few days, CopilotKit spent months repairing surfaces after its 1.50 rewrite, and the AI SDK took three major versions in fourteen months. Budget a recurring monthly upgrade session, pin everything, and let evals catch regressions. That is the same discipline the observability and backups ships already run under.

## 6. Modularity and per-client customization toward SaaS

The copilot route has a clean seam here that the original lacks. A client is a set of dependencies passed into every agent run (identity, compliance profile, style guide, preferred sources, budget) plus a set of capabilities switched on for them. Those live in the registry as data. A settings panel in the portal reads and writes that data. Until the panel exists, the same data is edited by us. The original route would need a tenant column added to state and threaded through fourteen agents by hand before any of that is possible.

Authentication and tenancy at the portal level come from Open WebUI's groups, roles and single sign-on, with Cloudflare Access in front. Inside the Next.js module, Better Auth (self-hosted, MIT, organizations plugin) fits the Doppler-managed posture better than a hosted provider. Feature gating per tenant has a standard package in the Next.js world (Vercel's flags SDK).

## 7. Scalability and load

The copilot route's serving layer is a stateless endpoint per request with per-thread state externalized, which scales horizontally. Two documented traps: a built-in agent instance refuses a second concurrent run, so instances are created per request, not at module scope; and the default in-memory runner is single-process, so real deployments need a shared session store. AG-UI streams over server-sent events, one held connection per active agent turn, no sticky sessions needed if thread state is external. The heavy work (grant generation) runs in the durable engine, not in the web tier, so load on the surface is bounded by concurrent reviewers, not by document size. The original route's load profile is LangGraph Cloud's, priced per node execution, which is the cost line that spiked in July.

## 8. User journey and experience

The original journey is a form, a wait of unknown length, and a markdown document in an inbox. That is the experience of a batch job, and it reads as an early prototype regardless of output quality.

The copilot journey is a workspace: the intake becomes a conversation that fills a structured brief; the agents show what they are searching and citing; the reviewer approves the learning objectives before the curriculum is drafted; a citation panel lists every source with its PubMed link; the grant narrative is edited in place and the agents revise around the edits. Interface elements are generated from typed data, so a citation table is a table, not a paragraph. That is the difference between a tool a program director uses and a tool they forward to someone else. Design quality is still our job; the stack removes the excuse, it does not supply the taste.

## 9. Maintainability by Claude, autonomously

This is where the routes separate most. The original route is fourteen files of prompt chains with free-text parsing; changing one section's behavior means reading the chain, guessing the parse, and re-running the whole pipeline to see the result. There are no output evals, so I cannot tell whether a change helped.

The copilot route gives me typed contracts (a schema change fails loudly), tools with signatures (a grounding change is a function), evals with scores (a prompt change has a number), traces in Langfuse (a bad run has a record), and versioned prompts as capabilities (a client change is data). With those in place I can run the loop you want: read the trace, propose the change, run the eval, ship if the score holds. Without them, autonomy is guesswork, and the last three days showed what guesswork costs.

## 11. Verdict and recommended shape

**The copilot route wins on every criterion except that it is more to build up front than patching, and patching is not on the table.** It is the more powerful approach and, once the shared foundation exists, the easier one to keep building, because every later agent is schemas, tools and evals rather than prompt chains and parsers.

Recommended shape, for the Track 6.3 spec when Portage 1.0 is done:

1. **Agents on Pydantic AI 2.x** with typed outputs on every boundary, tools for PubMed, medkb retrieval and the registry, capabilities per client, usage and traces to self-hosted Langfuse, evals in pydantic-evals with a golden set built from the best outputs of the first pipeline.
2. **One AG-UI endpoint as the contract** between agents and any surface. Human approval is a tool marked as requiring approval, which the protocol turns into an interrupt.
3. **Durable execution** under every long run. DBOS first, because it runs on the Postgres we already operate and back up; Temporal if DBOS proves limiting.
4. **One client library, not two.** CopilotKit's open-source runtime today, because its Pydantic AI integration is the most documented and it is already in the app; keep the AG-UI endpoint as the boundary so assistant-ui's adapter remains a drop-in alternative. Do not run both in one app.
5. **Our own thread store in the registry database** rather than the paid persistence tier, unless the paid tier's inspector and multi-tenancy turn out to be worth the seat price once there are real users to count.
6. **Surface as a module inside the Open WebUI portal**, with identity from the portal session and tenant context from the registry.
7. **Pin every version**, schedule a monthly upgrade window, and let the evals and traces decide whether an upgrade ships.

## 12. Decisions this leaves for Stephen

- CopilotKit free runtime with our own thread store, or the paid Intelligence tier self-hosted. Recommendation: free runtime now, revisit at first paying client.
- DBOS or Temporal for durable execution. Recommendation: DBOS.

## Amendment, 2026-09-16 (after the durable-execution and requirements research)

Three findings from the later research passes adjust section 11:

1. **Human approval lives in the database, not in the durable engine.** Pydantic AI's deferred tools end the run; message history is persisted by conversation id; the run resumes with the approval result days later. DBOS durability is scoped to the generation phase only. The recommended shape's item 2 stands, but the approval wait is a Postgres row, never a parked workflow.
2. **AG-UI streaming from a durable run is not wired today** (pydantic-ai issue 6580, open), and every engine buffers streaming across the durable boundary. The surface therefore shows step-level progress bridged over our own channel during generation, and token-level streaming only for interactive, non-durable turns (intake conversation, edits). This is a design decision for the spec, not a blocker.
3. **Provenance is a product requirement.** ACCME's 2026 AI guidance requires named human reviewers, version control and traceability, tool name and version and date disclosure, and documented bias screening. Every artifact the system produces records model, version, prompt version, reviewer and timestamp, and the review step cannot be switched off.

Also: pydantic-evals' judge defaults to an OpenAI model and must be overridden; CI regression gating comes from Langfuse experiments; documents render through Pandoc from Markdown plus CSL-JSON. Details in `2026-09-16-durable-execution-and-pydantic-ai.md` and `2026-09-16-cme-requirements.md`.
